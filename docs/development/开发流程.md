# 研发、审查与 Git 流程

## 从任务到交付

1. 阅读当前规则与任务依赖，检查Git状态；本机环境与用户改动按事实处理。
2. 每次选一个可验收的行为，写规则ID、初始状态、命令、事件、最终状态、错误场景。
3. 需要新裁定时先记录最小场景；只等待受影响行为，继续独立任务。
4. 游戏规则与缺陷修复先写能说明缺失行为的失败测试，再最小实现。纯文档排版不强制写测试。
5. 先跑相关测试，再跑该里程碑必要全量检查；UI改动实际操作，网络改动多身份/多实例验证。
6. 单独一轮审查规则偏差、状态原子性、来源/持续期、私有信息与证据状态；不要把自己上一轮结论当验证。
7. 更新文档、卡状态、任务与风险；报告改动、测试、可运行方式与剩余范围。
8. 精确暂存相关文件，检查 staged diff，提交一个完整小任务。

默认一位负责人持续推进。确有用户授权或适用项目指令时才启用子Agent；历史派发Prompt不会自动授权创建新任务或代理。角色职责可在同一任务中分轮完成。

## Git与版本

main 始终可读、可校验、已有运行时后可演示。短期 feature/fix/docs 分支只对应一个任务，避免多个未完成大里程碑并行堆积。
提交前检查 git diff --check、文件清单、内容验证、受影响测试；基线提交用 docs(project): establish Goa2V1 restart baseline。
里程碑使用annotated tag；本批命名 restart-baseline-2026-09-10。工作成果提交到本地仓库，不自动创建远程或推送公开仓库。
后续如已有明确远程上传授权，可按该授权上传；凭据与账号状态不进入提交。
Unity创建后提交Assets和meta、Packages manifest/lock、ProjectSettings；排除Library、Temp、Logs、Builds、个人IDE设置和本地存档。
规则版本、内容版本、协议版本、程序版本独立记录；破坏兼容时提供迁移或明确拒绝，不静默载入错版。
来源证据中的历史个人路径允许原文保留；新版可执行工具与CI不得依赖它们。

## 质量门槛

文档/内容提交：UTF-8、无缺链接、结构与引用完整、哈希一致、正式内容无丢失。
规则提交：编译、针对性行为矩阵、非法命令原子性、序列化、确定性回放。
界面提交：合法目标一致、等待/确认/取消明确、数据不泄露、首屏可见、代表分辨率可读。
联机提交：总4玩家身份正确、每个响应操作者正确、私有投影、重连、重复/乱序/过期命令。
发布提交：独立Player构建、完整对局、长局稳定、日志、存档兼容、版本与回退。

## 缺陷处理

保存最小局面、命令、revision、规则/内容版本、预期与实际结果，关联BUG编号。
先复现，再补回归，修根因；“增加一个按钮让它继续”不能代替修正选择状态。
报告“已改代码”“已跑测试”“已实际启动”“已提交”分别准确陈述，不让用户猜是否需要启动服务。

## CI现状

本批提供本地验证入口与GitHub Actions配置，尚无远程仓库，因此远程CI未执行。
当前CI配置覆盖资料与纯C#核心；Unity Test Framework已在本机运行同源NUnit测试，Editor与Player构建、实际输入、后台/可视化场景和独立程序包均有本机证据。远程Unity CI尚未配置；联网未实施，本地交付不等于满足全卡联机发布门槛。
