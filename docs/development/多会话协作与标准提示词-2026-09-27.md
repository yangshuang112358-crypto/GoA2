## 工作隔离与合并规则

1. 本主对话持有集成分支的写入与合并职责。UI、联机各在现有独立工作树中工作，不写另一个工作树。
2. 若启用新卡牌会话，应在本次整合提交基础上创建独立 `feature/cards` 分支和工作树。路径由创建结果确定，不能与集成工作树重复。新会话开始写代码前必须明确交接；本主对话随后停止并行实现卡牌。
3. UI 负责 UI3D 资源、布局与展示；卡牌负责 core 规则、正式裁定、卡牌状态和场景；联机负责服务、传输、认证与会话适配。所有合法目标和规则结果来自核心，UI/网络不得重算一套规则。
4. `GameScreen.*`、`CardTextMarkup`、`CardDisplay`、Command/View/存档结构与 `IPlayerSession` 是交叉接口。各任务先说明所需接口增量，由总控确定一位实施者、一个基线和验收条件。不同分支允许各自提交可审查补丁，总控逐个整合；禁止整文件覆盖最新接线。
5. “网络化 GameScreen”单列为集成任务：按 `IPlayerSession` 合同一次接线，固定网络身份、只读本人投影、断线禁用提交；本地 1234 热座切换不得变成网络换身份功能。UI 分支已经接入不等于已联网。
6. 合并使用明确提交 SHA。先完成当前卡牌到可验收提交，停止启动下一张，再整合 UI，跑涉及的测试、构建与图形检查，提交并推送后恢复后续工作。保持 merge 历史，便于单独撤销本轮 UI 合并；不改永久回退引用。
7. 同一个 Unity 项目同一时刻只运行一个 Editor/测试/构建进程，期间不修改其输入源码。不同工作树的重型 Unity 构建优先排队，按机器内存再决定是否并行。真实 OS 键鼠测试在机器上独占，不能与其他自动输入或用户操作争抢焦点。
8. 每个角色只维护自己的交接文件，例如 `docs/handoffs/ui.md`、`network/docs/handoff.md`、`docs/handoffs/cards.md`；创建前检查已有等价入口，优先复用。总控拥有集成状态文档。文件是持久记录，不是自动消息/锁服务。
9. 待用户裁定的问题只暂停对应卡牌或接口，继续无依赖工作。既有“所有行动预览/撤回”及伺机待发障碍物待办不能因 UI 重做自行实施。用户新要求与规则、接口或其他任务相冲突时，先报告具体冲突与影响，再做依赖该决策的部分。
10. 没有新提交、状态变化或待裁定事项时不反复轮询模型。不以等待时间或用量为目标；完成标准达到就交付，不为凑时长扩展范围。
