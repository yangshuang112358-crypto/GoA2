# 逐卡实施手册

先阅读规则 R-AUTHORITY/R-TARGETS/R-EFFECTS 与对应牌原文、裁定。所有108张当前只有数据；机制关键词与合同草稿不是完整语义确认。

## 每牌合同

记录 ID、英雄、颜色、卡等级、先攻、动作数值、远程/范围、底部被动。
主要、次要、防御响应、紫卡持续分别写清；把每个文本动作拆成有序单目标步骤。
每步列：trigger、required、controller、chooser、target_kind/team/range/exclude/immunity、bindings、on_no_legal_target、events、duration、expiry、resume。
先判断发动前置是否整体满足，再区分执行中无目标终止。用户没有裁定的“最多/如果可能/否则/重复”保留问题。
合同草稿中的自动关键词仅是检索线索；看见“攻击”不代表所有步骤目标都enemy，看见“可以”也不代表整张牌可以任意跳过。

## 原语与特例

优先选择、移动/推动/放置/交换、攻击/防御、弃牌/取回、金币、效果增删、分支/重复。
普通牌用结构化Schema；难以清晰表达的少数牌使用注册处理器，仍保留序列化选择、来源、时间和测试。
不要先做万能脚本语言；先以真实代表牌证明解释器。
每个命令失败零修改；此前合法提交的独立步骤不被错误回滚。快照恢复应从同一待选择继续。

## 测试矩阵

每个适用案例写初态、命令、事件、终态与禁止副作用：
正常、上下距离边界、无目标、友敌/单位种类、免疫、障碍占位、强制/可选、选择者权限、空手、资源不足、序列中断、多目标顺序、重复、时序/到期、被动、防御弃牌、来源、快照、非法命令、已有牌联动、私有投影。
不适用项写理由，不能用一个正常测试替代矩阵。

## 状态

data_only → specified → implemented → behavior_tested → integration_tested。
升specified必须完整合同、实质歧义解决；升behavior_tested必须该牌矩阵通过；升integration_tested须阶段、效果交互、私有视图、保存恢复等适用集成证据。
人工验收另记日期与场景；v2“静电封锁已测试”不改变Goa2V1状态。
更新status时填实际测试链接；禁止自动批量升级。

## 最小示例任务

电击适合验证“攻击目标→可选额外目标→额外目标本人强制弃牌→回到原攻击”。
但U-007阵营冲突须先解决，不能为了示例省略。此任务先实现可序列化选择窗口与合法命令测试，再接牌；一次只做一个原语或紧密相关牌族。
