# 训练选型核对

第一阶段结束时没有安装训练库、没有训练模型。2026-10-07当时本机 base Python 3.13.13 与现存 markdown-mas-tutorial 环境均未装 torch、gymnasium、stable_baselines3、sb3_contrib。驱动471.51报告CUDA11.4；这不是已安装CUDA工具链或现代PyTorch兼容性证明。当时短GPU学习验证条件不满足，不更改驱动、不使用云或模型API。

用户随后授权“推进”：已在独立.venv-ai安装Python3.11/PyTorch2.5.1+cu118，采用自定义前馈PPO候选打分原型验证可变动作，未直接采用SB3固定输出。GPU前后向及整局推理通过，但系统内存余量触发4GiB保留线，转CPU短训；实现、接口及限制见[AI短时学习接线](../development/AI短时学习接线-2026-10-07.md)。下文候选选型与阶段录像要求保留为后续参考，具体实测以最新验收为准。

## 核对后的候选

1. [SB3-Contrib MaskablePPO 官方文档](https://sb3-contrib.readthedocs.io/en/master/modules/ppo_mask.html)：支持离散动作、Dict观察、无效动作过滤；不支持循环策略，Dict动作不支持。子进程环境须自己实现 action_masks，评测须使用对应 maskable 回调/评测器。不能把 RecurrentPPO 直接拼成带记忆的 MaskablePPO。
2. [RLlib MultiAgentEnv 官方文档](https://docs.ray.io/en/latest/rllib/multi-agent-envs.html)：可表示轮流、同时及混合行动；通过返回观察的 agent 集合表达谁下一步行动。适合真实决策者不断切换，但仍需自定义候选编码、遮罩与策略映射；并不自动解决本项目的暗选隐私和跨席位回报。

阶段二优先尝试独立 Python 环境中的前馈 MaskablePPO，先固定一个学习席位/团队，其他席位使用被冻结的基线/历史对手。C#持有规则，Python只做张量编码、训练及进程通信。训练器不能直接读取本批的权威存档目录。需要双向命令协议及终局/截断标记后再安装并锁定版本；本批没有声称通信层或库组合已验证。

可变候选不能让网络把“第17个动作”记成永恒语义。优先为每个候选编码命令类别、卡编号、目标实体、位置、模式，用共享打分网络对合法候选归一化。若为了初试使用固定最大容量，先扫描本批候选最大值并留余量；任何超限直接报错保存现场，绝不切掉合法项。SB3原生固定输出与这种候选打分并非直接匹配，须实现并验证自定义策略；可先用显式稳定动作词表做较小固定局面验证。

在前馈版本学到基本目标前，不引入记忆网络。需要记忆时先把公开历史编码为结构化特征，或者单独验证支持mask的循环策略。暗选每席分别保存隐藏状态，不能把前一个席位的本次动作塞入下一席位隐状态。团队共用参数不等于共用私有信息。

## 训练合同

主要目标为团队胜负。第一版只用真正终局 ±1，截断不是平局或失败；有价值函数时截断须按可引导终止处理，不能把它当真正终止。随后若加入中间奖励，先做刷金币、无效来回移动、拖延终局、送队友的对抗测试。优先采用与团队优势相关的有界势能差，并检验它不改变获胜目标。

初次规模：单worker验证；实测允许后试2，再试4；保留至少4个逻辑线程与约4GiB可用内存供交互，避免一次创建16个环境。显存目标先控制在4GiB以内，小MLP或候选打分网络，分别记录采样、编码、更新耗时；8GB显存并不保证GPU比CPU快。

模型/检查点除权重外必须保存源提交、规则/内容哈希、观察/动作合同、超参数、种子流、对手快照ID、评测摘要和训练游标。ArtifactContract先实现严格规则程序集/内容/格式核对；有差异拒绝加载，需要明确迁移或重新训练并重新评测。难度以后通过历史快照、搜索预算与可解释打法调整，不能读取未揭示选择。

固定局面、固定阵容课程与正式完整对局独立统计；最终评测保留不参与训练的种子和换边，比较随机、简单、历史对手池，不把击败随机称为“会玩”。后续1/8/24小时预算见第一阶段实测验收；需用户确认后安排，本批不会自动开始。

## 用户补充：阶段录像与可变胜利条件

2026-10-07 用户希望方便时录几段阶段性智力提升录像，并要求后续考虑更多水晶生命值或推进次数。本节记录后续验收要求，不代表授权无人值守长训，也不代表已有学习模型。

阶段录像优先保留基线、初次学习、历史对手池训练后的检查点。同一组测试局面、阵容、规则配置与换边对手用于对照，短片展示防御、目标选择、推进和配合，也保留明显失误；完整对局及未参与训练的评测另行保存。片头或配套清单记录策略/检查点、源码、规则配置、种子和评测结果，不能只选获胜片段证明变强，也不能把随机与手写简单策略的差异称为训练进步。没有可靠提升时如实报告持平或退步。

已有 Unity 原生重放验证及 tools/ui3d 的真实帧录制脚本可作参考；现有展示脚本会临时注入 GameScreen 演示代码，不能直接当作 AI 回放录像器。后续先明确最小回放播放、镜头与录制接线范围，优先复用现有重放，不重做正式 GameScreen。建议每阶段选取一至三分钟可比片段，并附完整回放。录像属于尽力提供的展示，不阻塞规则正确性与训练验收；本次尚未生成阶段提升视频。

规则核心已经存在 RuleSettings.StartingCrystalLife、RuleSettings.FrontlineVictoryMarks，GameState/GameView 保存 VictoryMarksRequired。当前 AI 观察只有双方当前水晶生命与推进标记，尚未显式包含初始水晶生命和胜利所需标记数。因此在开展变规则训练前，需要补充公开且不可变的规则配置观察，升级观察格式版本，并记录稳定配置 ID、实际参数、规则/内容哈希及模型支持范围。初始生命不能未经规则确认就当作生命上限；当前绝对值、目标阈值与剩余目标都应可表达，归一化不能丢掉这些含义。

变规则局应从正式规则配置创建，验证初始状态、真正终局、确定性与 Unity 重放一致性；不能用中途调试改血量的教学局替代正式评测。现有严格兼容检查需要明确区分已验证的参数配置与机制/内容变更，在迁移方案完成前继续拒绝不兼容加载，不能简单放宽哈希检查。规则变化后分别报告各配置的完整对局、截断和胜率，增加生命/推进目标会延长对局，需重新测量速度并调整步数上限，不能把因此增加的截断判作失败。

课程先固定默认规则，再逐步混合若干显式配置，保留未见过的参数组合与范围作独立评测。模型清单声明训练范围和验证范围；范围外配置须明确拒绝或重新评测，不能承诺旧模型自动理解新机制。奖励仍以团队真正胜负为主，任何中间奖励均需在不同目标长度下检查刷分、拖局及牺牲队友问题。具体新增参数数值在实施该阶段时确定，本次不修改正式玩法。
