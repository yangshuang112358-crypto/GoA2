## 1. 接手时先读这一页

**采用用户提出的顺序：优先完成六名英雄的满级紫卡，再完成剩余普通牌。** 原因是紫卡会改变行动边界、触发时机、重复、通行、数值和小兵战斗；先把这些公共机制落实，后续普通牌可以复用，已完成卡牌也能及早发现兼容问题。

“优先”包含先厘清六张紫卡的合同与共用接口，不等于同时写六张，更不等于先造一套庞大的通用引擎。实现仍逐张交付；遇到未裁定语义，暂停该分支，转下一张不依赖它的紫卡。六张都受阻时，才选第3节中的独立普通牌。**不能靠猜测把紫卡标为完成。**

## 2. 六张紫卡：优先级、合同拆解和影响面

建议顺序：**电闪雷鸣 → 重型枪械 → 幻化 → 斗篷与匕首 → 一人成军 → 潮汐之主**。前两张分别验证“行动后触发”和“数值/推动后触发”；中间两张验证行动前和重复；后两张共用小兵战斗子流程。顺序受裁定依赖约束，不要求等待第一张答复才分析下一张。

所有紫卡都应由`PlayerState.PurpleCardId`绑定持有能力，不能塞进手牌或要求打出紫卡。持有能力与普通限时`ActiveEffect`分开：击败时不能把紫卡所有权删除；英雄不在场时，哪些能力可产生新触发、已经排队的触发是否保留，须在各卡合同明确。

```text
  PrimaryCategory（保留基础攻击、基础技能与普通类别的区别）
  Cursor / Targets / SavedResults / RepeatIndex / TargetHistory
  CompletionMode（结算出牌 / 返回父行动 / 返回兵战或轮末）

TriggerRecord（建议字段）
  TriggerId / SourceAbility / ControllerSeat / CauseEventId
  CauseFrameId / TimingWindow / Payload / ProcessedState

ChoiceState：引用所属FrameId；候选、选择者、私有性、继续点可保存
```

执行约束：

1. 用户确认行动后进入适用的行动前窗口；预览、目标高亮与分段移动命令本身不是新的行动。Q-02未解的类别不得偷偷放进触发表。
2. 明确区分`AttackResolved`、防御后续结束、行动实例结束、整张牌结束。不要给旧日志事件增加隐藏副作用，使一次旧事件意外触发新紫卡。
3. 触发条件成立时登记一条有原因的记录；在合同规定的窗口执行，必要时挂起父帧。**反击必须等导致弃牌的行动完成，不在弃牌函数中立刻递归攻击。** 保存具体等待结束的行动实例；不要一律等待整条根卡链，否则重复行动可能把应执行的反击推迟到错误位置。涉及防御所属窗口或多触发竞争时先按合同确认。
4. 对行动触发按“能力来源＋行动实例＋窗口”防重；对弃牌、推动等事件触发用具体`CauseEventId`，不能每行动只触发一次而吞掉多次真实事件。重连/重试不制造第二次触发。
5. 执行帧包含实际使用牌，即使牌在弃牌堆，也不能去找“当前未结算揭示牌”冒充来源。当前`CombatRules.AttackTargets`、`ActiveCard`等存在该假设，须在反击之前隔离。
6. 重复重新执行适用的完整行动，重新取合法目标；牌文移动是内部步骤。用明确`RepeatPolicy`记录次数和不同目标规则；D-028普通上限与雷霆回旋镖的用户连续触发特例分别保留。Q-05未解，不能替虎爪选择上限。
7. 一个子帧只恢复一次父帧；只有最外层出牌流程调用牌区结算和推进先攻。胜利立即终止后续选择/触发，不再发第二次奖励。
8. 使用显式继续点/枚举和序列化数据，不保存委托闭包、Unity协程或UI变量。运行步数保护只是程序异常检测，不是强行截断合法重复链的游戏规则。

迁移方式：先为一张紫卡引入最小完成窗口；需要嵌套时再引入帧。旧引擎继续原路径，新引擎通过受控入口接入；当前`Execution`若保留为顶帧适配器，不得和另一份可变栈同时成为权威。先验证旧单行动行为不变，再接第二个消费者。无需一次性把所有65张牌换成新的DSL。

### 4.3 用上下文查询效果，避免互相污染

建议的查询边界示例：`CanAffect(context)`、`CanTraverse(context)`、`CanEndAt(context)`、`GetStatBreakdown(context)`、`GetCombatMinionTraits(context)`、`GetMinionBattleContribution(context)`。名称可调整，语义必须明确：

| 需求 | 正确分离 | 典型错误 |
|---|---|---|
| 基础行动 | 先看本次实际行动模式，再看正式类别 | 用银色/金色或`family`猜；银卡拿来次防也触发基础技能后 |
| 免疫 | 全免疫、仅攻击、非相邻远程、排除原攻击者、仅敌方行动分别匹配 | 反射屏障阻止带远程图标的技能；有任意免疫就取消本人行动 |
| 穿越/落点 | 中间格与终点独立；地图边界、地形、单位、地图部件分别判定 | 允许穿过单位就允许落在单位上或无视静电封锁 |
| 位移限制 | Move/Push/Place/Swap分别声明；来源英雄与被移动单位分别记录 | 不能移动就不能被推；有铜墙铁壁就默认禁止所有放置 |
| 条件存在 | 存在条件与被作用目标两条查询 | 免疫单位不再计入相邻敌人数/友方支援；把受保护重兵从存在条件中删除 |
| 视为小兵 | 一人成军只在小兵战斗上下文贡献数量 | 将布罗根`UnitState.Kind`永久改成小兵，被指挥移动或给背刺提供两次支援 |
| 视为阵营/兵种 | 魅惑、演练等只修改本次战斗计算视图 | 更改真实队伍或兵种，影响推进出生、重型保护和胜利 |
| 中毒 | 升级图标值按标记规则转换；保留原始获得记录 | 将总攻击/先攻取负，连牌面及重型枪械+2一起反转 |
| 来源结束 | 临时效果依D-026/027取消；紫卡持有能力另行匹配 | 吟游诗人取回一张普通牌，顺便关掉永久紫卡；复活重复叠加紫卡 |

数值示例：只有2个攻击升级图标时，其中毒贡献按牌文从`+2`变为`-2`，不是总攻击减2，也不是把全部攻击取负。两种毒叠加/覆盖尚未裁定，此例不推导叠加规则。

### 4.4 统一结果事实，但不要统一不同游戏语义

- 弃牌入口应携带来源、所有者、原因（防御/代价/受迫/交换等）及所属行动。先枚举现有所有`CardDiscarded`写入点，再接反击；交换是否算弃牌按规则核对，不能看到牌区变化就触发。
- 推动结果至少区分：合法但受阻0格、实际移动、由于免疫/保护而根本未执行、地图边缘停止；同时保存发起者、单位、起终点、原因。重型枪械监听什么结果由Q-06决定。
- 击败与移除分离：击败才进入相应奖励与防止窗口；兵线移除不是攻击击败。巩固防线不能凭“对象要消失”保护轮末移除；一人成军也不是所有击败免疫。
- 地图上的可移动部件与英雄持有的中毒标记分离。108张现有牌没有提供完整地图部件生成目录，不能为了让控物等可测而偷偷发明正式生成规则。调试构造只作验收入口。
- 石化必须保存原英雄身份、所有者和位置。是否锁定目标/动态重算、还在哪些查询中视为英雄待合同确认；不可直接覆盖`Kind`后丢失恢复信息，也不能由“最近目标变成地形”引发反复选中/取消的循环。

## 7. 提效工作流：少重复阅读，保留必要验证

### 7.1 每张卡的最小任务包

一次准备以下内容，后续只更新差异：

```text
目标：卡ID / 正式文本与数据入口 / 当前状态
合同：步骤、选择者、强制或可选、合法目标、失败/无目标、时点、来源、到期
前置：已裁定依据 / 尚待答问题 / 所用公共机制
改动：预计触及的3—6个文件；同族参考卡与参考测试
联动：本指南第5节适用行；哪些组合不可能正式共存
证据：新增失败用例 → 修复后专项 → 必要回归 → 构建与手工入口
交付：提交、状态、已知限制、下一张及需要读取的最少文件
```

同族只比较实际差异：距离、兵种过滤、重复次数、可选性、时点和被动图标。例如保卫→持盾→巩固防线共用防止击败机制，但最后一张增加重型推进分支，不能只改目标过滤后复用原测试结论。

### 7.2 代码和测试的节奏

1. **一张卡/一个可验收公共能力为一个小提交。** 复杂紫卡可分“前置机制提交”和“完整牌提交”，前者不开放未完成牌。
2. 新规则先用最小失败用例证明缺口，再最小实现。已有共享机制用参数化差异测试；不为每张牌机械复制同一套恢复/隐私测试，但每种新增待选择必须验证保存恢复。
3. 迭代时跑专项及受影响机制；可验收提交前按项目要求跑完整回归。新的失败或新修改才重跑相应检查，不在未变化代码上反复执行同一全量套件。
4. 全量回归没有必要每几秒轮询输出；开始一次、等待结束、读摘要，失败再读具体用例。同一Unity工程只启动一个批处理进程。
5. 一份手工预设覆盖主要路径，顺手放置可行的简单分支；**从完整行动开始前加载**，防御/弃牌场景也从攻击者行动起点开始。右侧最近记录输出步骤和分支，不从已被攻击的半途窗口开始。
6. 复杂交互优先做能证明时序/恢复的自动化用例，不为凑预设数量造大量相似局面。不要用沙盒强制装配不可能共存的升级牌，冒充正常对局联动。
7. 状态由事实推进；构建、Editor规则测试、独立Player执行、真实UI操作、联网分别记录。继续如实报告Windows应用控制限制，不重复尝试未改变的受阻入口、不绕过系统策略。

**应节省的开销：** 重读所有历史、复制大段牌文到多个文档、每轮输出巨量源码、无变化重复构建、重复制造已验证的同族场景。**不能省略：** 实质语义确认、来源/选择者、非法命令原子性、嵌套恢复、旧档兼容及关键联动回归。

### 7.3 每类公共机制的验收门槛

| 机制 | 必须有的证据 |
|---|---|
| 触发/执行帧 | 触发0次/1次/合法多次；父流程只恢复一次；每个新增选择窗口保存恢复；重试无重复副作用；无空悬的等待 |
| 目标与位移 | 边界距离、双方/自身/单位种类、免疫、空目标、占位、不同移动模式；额外范围不误当远程 |
| 替换/兵战 | 支付/不支付、重型保护、奖励差异、推进与出生、轮中不升级、胜利立即停；多来源竞争仅采用已裁定顺序 |
| 持续/身份/数值 | 创建/激活/到期、来源取回/击败、真实身份不变、上下文差异、修正来源、第四回合的下回合效果不跨轮 |
| 牌族具体绑定 | 全文与正式ID/版本匹配；当前参数差异及次要/快速替代；开放整张而非半张；合法UI入口与手工说明 |

### 7.4 旧版本与存档

沿用[引擎版本ADR](../architecture/decisions/ADR-003-规则引擎版本.md)，不为了减少代码删掉旧引擎分支。新增帧/触发/兵战状态必须进入权威存档与重放；缺省字段不能改变冻结旧档含义。新增状态后，显式引擎升级条件也要检查“没有挂起帧、队列或待兵战”，不能只沿用目前`Execution == null`的判断。

在改变相关行为前冻结有意义的旧选择窗口；保存完整输入、版本与哈希。金钱、弃牌、触发次数和主动/被动来源都要在重放后相符；事件文案不承担执行逻辑。不得把文档中的建议类型名写进旧档并假称兼容已验证。

## 8. 下一次获准实施时的具体起步任务

1. 读取当前状态与本指南，确认工作树；不自动把已经过期的“下一张巩固防线”作为最高优先级。
2. 为六紫卡各列一份短合同，复核第6节待决项；把需要用户判断的部分集中给出最小场景。没有答案时不启动依赖该答案的开放实现。
3. 优先以电闪雷鸣验证行动完成窗口、选目标/本人弃牌及保存恢复；若U-014未解，先做与目标筛选无关的已确定公共边界，或切到已裁定的下一张紫卡。不得将预备工作计入新增完成数。
4. 保留现有路径，逐步提取行动收尾，再处理推动事件、行动前窗口与重复；兵战两张共用一次独立子流程拆分。每个共享改动按第5节明确影响的已实现牌。
5. 六紫卡之后按第3节推进普通牌。每张实际验收提交后直接继续授权范围内的下一张，不因完成一张就反复询问是否继续。

这套顺序的预期收益来自：紫卡提前验证规则接口，同族共享算法，关键联动集中覆盖，文档按需读取。它不能保证固定token或工时下降比例；第一次落实帧/触发/兵战边界仍有成本，但可减少后续反复修改主流程。
