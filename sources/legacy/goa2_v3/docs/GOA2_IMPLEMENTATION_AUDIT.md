# GoA2 当前实现审计与完成差距

审计日期：2026-06-13

审计对象：`goa2_v2`、`goa2_v3`、线程“整理GoA2规则与角色卡面”及当前指导线程。

## 1. 总结

当前项目并不是“v3 已经复刻 v2”。

- **v2** 是功能较多但规则耦合、卡牌特判集中、测试覆盖较少的可玩原型。
- **v3** 是后端权威、可序列化、测试较好的四席热座规则沙盒，但只完成到选牌、翻牌和基础移动。
- **完整 GoA2** 还需要攻击、防御、伤害、死亡、复活、兵线、升级、回合循环、多人房间和 108 张卡牌效果。

因此正确路线不是继续做纯展示，也不是立即批量实装 108 张卡，而是先让 v3 恢复 v2 的基础数值玩法，再按规则机制和卡牌族群迁移。

## 3. 当前指导线程完成了什么

当前指导线程的有效工作：

1. 审查了 v2 的提交阻止项。
2. 修复并测试了强制弃牌不可跳过：
   - 电击类攻击前弃牌；
   - 偏转/反射屏障；
   - 电闪雷鸣；
   - 推动受阻队列。
3. 建立了 v2 基线提交。
4. 创建并逐轮推进了 v3：
   - 规则核心骨架；
   - 地图和卡牌展示；
   - 选牌/确认/翻牌；
   - 四席热座；
   - 调试面板；
   - 后端权威地图移动。
5. 建立了独立 v3 Git 仓库。
6. 持续通过另一个 Codex 窗口执行、由当前窗口审查和纠偏。

当前指导线程偏离用户想法的地方：

- v3 初期过度强调最小引擎骨架，缺少可识别的游戏体验；
- 第一版网页只是技术 demo，不接近 v2；
- 规则说明没有先从原规则线程建立权威基线；
- v3 先实现了单席流程，之后才迁移四席；
- 当前仍未优先恢复攻击、防御、回合、兵线等 v2 核心玩法；
- “卡牌状态为已实装”的目录部分沿用了 v2 代码存在性，不等于经过 v3 行为验证。

本次新增的两份文档就是对此进行纠偏：后续任务必须同时引用规则说明书和本审计。

## 4. 距离“复刻 v2 基础玩法”还差什么

“复刻 v2 基础玩法”不要求全部复杂卡牌效果，但至少要求可以完成一局数值版对战。

### P0：形成可循环对局

- 基础攻击目标选择；
- 小兵/英雄目标；
- 伤害计算；
- 防御弃牌或放弃防御；
- 击败与复活；
- 当前卡牌行动完成；
- 四张牌按先攻逐一结算；
- 进入下一回合；
- 5 张牌用尽后进入轮末；
- 轮末回收并开始下一轮。

### P0：兵线与胜负

- 地图上的小兵状态；
- 小兵阻挡移动；
- 小兵伤害修正；
- 轮末数量差；
- 队长选择移除；
- 重型最后移除；
- 战线推进与重生；
- 水晶生命与战线胜利。

### P1：升级与经济

- 击杀金币与助攻金币；
- 升级支付；
- 三色升级门槛；
- 候选牌替换；
- 永久被动；
- 紫色卡展示；
- 未升级补偿金币。

### P1：基础行动完整性

- 快速移动；
- 主要移动；
- 次要防御；
- 决策币；
- 队长同速选择；
- 复活后继续卡牌结算；
- 调试 `+1 金`、`+99 金`、`轮末`、`击杀`。

达到以上范围后，v3 才能称为“复杂卡牌效果尚未全部实装，但基础数值玩法达到 v2 水平”。

## 5. 距离“完整完成”还差什么

### 5.1 规则引擎

- Command 和合法性校验统一入口；
- Event before/after；
- Triggered Effect；
- Continuous Effect；
- Replacement/Prevent Effect；
- 效果来源、持续时间、作用目标和失效条件；
- 同时触发排序和优先级；
- 选择窗口与等待玩家响应；
- 可选/强制元动作；
- 失败元动作终止卡牌；
- 确定性随机与事件日志。

### 5.2 卡牌系统

108 张卡牌需要逐张建立：

- 规则语义审查；
- effect schema 或 handler；
- 正常行为测试；
- 无合法目标测试；
- 免疫/阻挡测试；
- 多效果联动测试；
- 升级被动测试；
- UI 选择流程测试。

不能用“代码里有这个卡牌 ID”直接标记为已完成。

建议状态：

- `data_only`
- `specified`
- `implemented`
- `behavior_tested`
- `integration_tested`

### 5.3 多人联机

- Room；
- Player identity/token；
- 每个客户端的私有视图；
- 服务端权威 action；
- revision/optimistic concurrency；
- polling、SSE 或 WebSocket；
- 断线重连；
- 房间恢复；
- 防止客户端查看其它玩家手牌；
- 回放与审计日志。

四席热座只能作为规则测试工具，不能替代真实多人同步。

### 5.4 产品体验

- 大厅与选英雄；
- Ban/Pick 预留；
- 玩家名、英雄名和队伍；
- 顶部公开出牌区；
- 统一地图选择确认/取消；
- 合法目标高亮完全来自后端；
- 卡牌关键词着色；
- 卡牌编辑器与状态目录；
- 调试工具；
- 错误提示与行动日志；
- 响应式布局与多窗口测试。

## 6. 推荐开发顺序

后续不再按“看起来容易的模块”推进，而按可完成一局游戏的依赖顺序推进。

1. 基础攻击、伤害、防御入口。
2. 击败、金币、水晶生命、复活。
3. 卡牌按先攻逐一行动和回合结束。
4. 决策币和队长同速选择。
5. 小兵与兵线。
6. 一轮结束与卡牌回收。
7. 升级和永久被动。
8. 快速移动。
9. 建立通用效果生命周期。
10. 按机制族群迁移卡牌，而不是按文件顺序硬编码。
11. 最后接入真正多窗口房间同步。

## 7. 卡牌迁移分组

建议按规则机制分批：

1. 纯数值攻击、移动、防御；
2. 攻击前/攻击后；
3. 弃牌与取回；
4. 推动、拉动、放置、交换；
5. 免疫、禁止指定、行动封锁；
6. 持续到本回合/下一回合/本轮；
7. 重复攻击与条件循环；
8. 范围目标与多目标选择；
9. 替换、阻止与反射；
10. 终极持续效果。

每组先做引擎原语和机制测试，再接具体卡牌。

## 8. 对 Codex 的约束

后续 Codex 任务必须：

- 先引用 `docs/GOA2_RULEBOOK.md` 中对应规则；
- 不以 v2 当前实现替代规则说明；
- 不把卡牌 ID 特判写进主回合流程；
- 所有合法目标由后端计算；
- 所有状态变化可序列化；
- 失败命令不得部分修改状态；
- 新规则先写测试；
- 复杂卡牌至少一个正常测试和一个边界测试；
- 每轮只完成一个可验收纵切片；
- 提交前运行全部测试并报告未实现范围。

## 9. 文档还是 Skill

当前阶段选择项目文档，而不是 Skill，原因：

- 规则仍存在待确认项；
- 文档需要跟随 Git 和代码版本审查；
- 不同卡牌的实现状态变化频繁；
- Skill 更适合稳定后的工作流约束，不适合承载仍在修订的游戏规则。

当以下条件满足后，再创建 `goa2-rules` Skill：

- 核心规则没有重大待确认冲突；
- 基础对局在 v3 可完整运行；
- 卡牌 effect schema 稳定；
- 规则说明书有版本号；
- 已建立卡牌状态清单和测试模板。
